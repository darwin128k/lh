# lh против LVGL: время кадра

Машина: i7-13700K, **без AVX2**; GCC 5 и MSVC в обоих билдополняющих.
Время на кадр в микросекундах. Единственная разница между сценами — шрифты:
Roboto у `lh`, Montserrat у LVGL, оба 16px 4bpp.

Сцены: `scene_lh.c`, `scene_lvgl.c`, общий каркас — `main.cpp`.

## Окно gl рисует только изменения (2026-11-24)

Раньше окно gl забирало повреждения и рисовало весь кадр, так что частичная
перерисовка из этого бенча в продукте не использовалась. Теперь обновление отдаёт
системе каждый изменившийся прямоугольник, а `paint` рисует ровно то, что
попросила система (изменения и открывшиеся области).

Замер на настоящем окне 800×600 с 48 карточками: одна карточка меняет цвет,
окно обновляется, перерисовка засекается (100 раз, поочерёдно старая и новая
сборки, медиана / p90, мкс):

| | до | после |
|---|---|---|
| круг 1 | 888 / 1460 | **76 / 109** |
| круг 2 | 1256 / 1764 | **53 / 98** |
| круг 3 | 1431 / 1855 | **90 / 111** |
| пикселей за перерисовку | 480 000 | 8 100 |

## Распаковка глифа в ядре (2026-11-24)

Приём gl «восемь 4-битных пикселей одним словом, распаковка в регистре» теперь
в ядре (`lh_pixel_mask_get_coverage_8`), gl зовёт его оттуда. Текст gl тот же
по времени, все картинки те же до байта.

## Перенос строк в ядре (2026-11-24)

Перенос строк переехал в ядро (`lh/core/str/wrap.h`): ширину символа ядро
спрашивает у шрифта через callback, gl переносит подписи им. Все картинки те же
до байта.

Текст gl до и после переноса в ядро (сборки поочерёдно, медиана из 7):

| Сцена | до | после |
|---|---|---|
| text, gl | 297 / 265 | 281 / 284 |
| partial text, gl | 61.6 / 60.2 | 61.1 / 67.1 |

То есть без изменений, в пределах шума.

Попутно: GCC 16.1 с LTO неверно вывел известные биты аргумента вида
`max(width, 0)` (IPA bit-CP) и выбросил перенос из клона
`lh_str_wrap_measure.constprop.isra` — в бенче подписи gl перестали переноситься,
тесты при этом проходили. Ширина больше не передаётся как `max`.

## SIMD-спаны gl переехали в ядро (2026-11-19)

Альфа-строки gl (SSE2 по четыре пикселя, скалярная полоса над одним
непрозрачным словом) теперь в ядре (`lh_pixel_span_blend_alphas_argb`). Две правки сверх переноса: прозрачные
края строки не обходятся, а строка короче 16 пикселей уходит в SSE2 целиком —
искать в ней отрезки дороже, чем её блоки. Все 21 картинка та же до байта.
Старая сборка (HEAD в отдельном worktree) и новая запускались поочерёдно,
медиана из 5:

| Сцена | до | после |
|---|---|---|
| shadow, gl | 687 / 694 | **534 / 540** |
| cards, gl | 198 / 198 | 194 / 196 |
| text, gl | 242 / 236 | 242 / 237 |
| partial shadow, gl | 18.4 / 18.8 | **16.9 / 17.4** |

Первая версия без правки коротких строк замедляла текст gl на 8–10%: глифы gl
шли по восемь пикселей через вызов ядра, а не встроенный блок; восьмипиксельная
форма переехала в ядро целиком (`lh_pixel_span_blend_alphas8_sse2_argb`).

## Градиент переехал в ядро (2026-11-19)

Градиент, таблица его 256 цветов и проход по строке теперь в
`lh/core/pixel/gradient*`, в `0xAARRGGBB`. Проход выдаёт позиции (байты), а
цвета находит таблица — так один проход служит любому типу цвета, и gl с его
`lh_gl_color_t`. Картинки gl те же до байта (сверено `--dump`).
Цена — второй проход по строке. Старая сборка (HEAD в отдельном worktree) и
новая запускались поочерёдно, дважды, медиана из 7:

| Сцена gl | до | после |
|---|---|---|
| cards | 191 / 216 | 191 / 200 |
| grad_vertical | 307 / 311 | 308 / 313 |
| grad_diagonal | 673 / 753 | 739 / 747 |
| grad_radial | 1003 / 1051 | 1063 / 1123 |
| partial grad_diagonal | 30.0 / 30.4 | 31.5 / 32.5 |
| partial grad_radial | 42.4 / 42.6 | 45.0 / 45.3 |

Радиальный кадр дороже на 6%, диагональный на 3–5%, вертикальный (столбец)
не изменился; LVGL на радиальном — 1200–1247.

## Что изменилось в коде

`lh_gl_gradient_sampler_t` (include/lh/gl/gradient/sampler.h, src/lh/gl/gradient/sampler.c):
таблица цветов из 256 шагов строится один раз на заливку, а не считается на
пиксель.

- **Таблица цветов на 256 элементов.** Вход `lh_gl_gradient_color_at` и раньше был
  `lh_byte_t`, то есть цвет квантовался в 256 шагов. Таблица — вынос, не
  приближение: биты совпадают с прежними.
- **Деление с переносом остатка.** Между стопами каналы считаются как
  `(from * (span - at) + to * at) / span`, но частное и остаток несут дальше, а
  не делят заново на каждом шаге.
- **`reach[256]`** — таблица квадратов расстояний для радиального градиента,
  чтобы не брать целый корень на пиксель.
- **Инкрементальный обход.** `dx`/`dy` считаются один раз на строку, каждый
  следующий пиксель — `+2` вдоль; деление линейного случая выполняется один раз
  на строку, дальше едет остаток.
- **`lh_gl_canvas_fill_colors`** — пачка из `LH_GL_CANVAS_BOX_RUN` цветов за один
  вызов canvas, вдоль оси. Вертикальный градиент раньше слал по одному
  `fill_pixels` на строку; теперь читает колонку и отдаёт полосу целиком.

## Как это читать

- **Просадки больше нет нигде.** Единственное отставание — вертикальный градиент,
  1.11x, и это внутри шума.
- **Надёжно читаются только расхождения больше ~1.2x.** На этой машине Google
  Benchmark даёт CV 9–15% на замер. Значит выигрыш `flex` 0.75x, `partial cards`
  0.74x, `partial shadow` 0.37x — настоящий, а `cards` 0.87x, `grad_diagonal`
  0.92x, `text` 0.85x — в пределах разброса.
- **Частичная перерисовка — где выигрыш самый честный.** Там объём работы мал,
  разница с LVGL до 2.7x, и она переживает любой шум.
- **Худшая сцена теперь ~1 мс** (радиальный градиент 1030 µs, тени 1024 µs)
  против 10 мс до оптимизации. Для браузерного редактора это снимает главный
  риск: софтверная отрисовка в wasm больше не упирается в заливку фона.
- Это нативный замер. **Для браузера множитель wasm всё ещё не измерен** —
  нативные числа остаются нижней границей, а не оценкой.
